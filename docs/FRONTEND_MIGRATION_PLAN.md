# Frontend Migration Plan — Phase 8.2

Architecture decision: the Python backend (optimizer, projection engine, decision
engine, football intelligence, market intelligence, data pipelines, live systems)
stays authoritative and unchanged. The frontend is rebuilt as a real React app so
the components researched in `docs/UI_21ST_RESEARCH.md` can be adopted close to
their real implementation. This document is the concrete plan for that boundary
and the staged rollout — written before any mass implementation, per the phase's
own explicit "stop and review" checkpoint.

## OLD → NEW

```
OLD:
SQLite (data/fpl.db)
  -> Python renderers (monitoring/dashboard/*.py) each return an HTML string
  -> assemble.py concatenates them into ONE big data/dashboard.html
  -> a plain http.server (or sse_server.py's static-file branch) serves it
  -> vanilla <script> JS in the page: ~10s live_snapshot.json poll + SSE
     EventSource('/events') patch specific DOM ids in place

NEW:
SQLite (data/fpl.db)                                    [UNCHANGED]
  -> Python model/optimizer/decision layer               [UNCHANGED]
  -> NEW: monitoring/api/ — one JSON-payload builder per screen, each a thin
     shaping pass over the SAME already-computed objects the HTML renderers
     read today (never a second computation, never a duplicate query)
  -> sse_server.py gains a handful of new GET routes (/api/command,
     /api/myteam, /api/plan, /api/football, /api/scout, /api/advanced,
     /api/live) serving those payloads as JSON, alongside its EXISTING
     /events SSE stream and static-file serving (same process, same port,
     zero new infra)
  -> frontend/ — a real React + TypeScript + Vite + Tailwind + shadcn/Radix
     app. Each screen fetches its own /api/<screen> payload on mount/nav and
     subscribes to the SAME EventSource('/events') stream for live push,
     reusing the existing message shapes verbatim.
  -> data/dashboard.html keeps being generated by the OLD path, untouched,
     as the fallback until the new frontend is validated screen-by-screen
     (Part 19's own "don't delete the old dashboard immediately")
```

Nothing about *how a number gets computed* changes. Only the last hop — HTML
string vs. JSON object — is new, and even that reuses the existing
`data_payload.py::build_workspace_payload` pattern (already a real, working
precedent for "shape already-computed objects into JSON, never re-derive").

## Why this boundary, not another one

Three options were considered:

1. **Keep server-rendered HTML, add React only for islands of interactivity**
   (e.g. htmx-style). Rejected — doesn't get us the shadcn/Radix component
   ecosystem the whole point of this phase is to adopt; still fighting string
   templates for the parts that matter most (Command hero, Scout table, Plan
   rail).
2. **Full SSR with a Node backend proxying to Python.** Rejected — a second
   runtime/process class this single-laptop, free-resources project doesn't
   need (mirrors the same reasoning `sse_server.py`'s own docstring already
   gives for rejecting a message broker: "real complexity this project
   doesn't need"). A static-built SPA talking to the existing stdlib Python
   server is simpler and keeps exactly one server process.
3. **Static-built React SPA + Python JSON API + existing SSE server for live
   push.** **Chosen.** Reuses 100% of the existing live-data infrastructure
   (`sse_server.py`, `live_snapshot.py`, the SSE message shapes the current
   vanilla JS already parses), adds one new thin layer (JSON shaping), and
   keeps the deployment story identical: one Python process, one port, a
   `dist/` folder of static assets instead of one `dashboard.html` file.

## The new `monitoring/api/` layer

One module, mirroring the existing per-screen renderer split
(`command.py`/`myteam.py`/`football.py`/`scout.py`/`plan.py`/`legacy.py`
[Advanced]/`match_centre.py`):

```
monitoring/api/
  __init__.py
  command_payload.py    build_command_payload(conn, *, ta, ca, sd, current_rec, freshness, locked) -> dict
  myteam_payload.py      build_myteam_payload(conn, *, locked, ta) -> dict
  plan_payload.py        (extends data_payload.py::build_workspace_payload — already real JSON)
  football_payload.py    build_football_payload(conn, squad_ids, decision_snapshot) -> dict
  scout_payload.py       build_scout_payload(conn, squad_ids, considered_ids, ta, locked) -> dict
  advanced_payload.py    build_advanced_payload(conn, squad_ids, ta) -> dict
  live_payload.py        (extends live_snapshot.py::build_live_snapshot — already real JSON)
```

Each function's contract: **take the exact objects `generate_dashboard_html`
already computes once per regen, return a dict of exactly the fields the
corresponding screen's HTML renderer already shows.** No payload invents a
field the HTML version doesn't already have — this is a reshaping pass, not a
new feature surface. Concretely, most of these functions will call into the
SAME real dataclasses the HTML renderers already read
(`AuthoritativeDecision`, `CaptainOption`, `TransferOption`, `FootballSignal`,
`PlayerCandidate`, `DecisionSnapshot`, `FreshnessResult`) and serialize their
existing fields, rather than re-deriving anything from the renderer's HTML
string.

### The one real refactor this requires

`assemble.py::generate_dashboard_html` currently computes its real inputs
(locked squad, `ta`/`ca`, `sd`, freshness, live payload, decision snapshot,
squad ids, considered ids, etc.) and composes HTML **in the same function**.
To avoid a duplicate "compute all the real inputs" pipeline (explicitly
forbidden — "do not create duplicate data pipelines"), that setup phase needs
to be extracted into one reusable function:

```python
@dataclass
class DashboardContext:
    conn: sqlite3.Connection
    locked: LockedSquad | None
    ta: TransferAnalysis | None
    ca: CaptainAnalysis | None
    sd: dict | None                 # cached strategic_plan decision detail
    current_rec: dict | None
    freshness: FreshnessResult | None
    live_payload: dict | None
    squad_ids: set[int]
    considered_ids: set[int] | None
    dash_state: str
    # ... every other real input the HTML renderers currently close over

def build_dashboard_context(conn, live_payload=None, gw_window=1, ...) -> DashboardContext:
    ...  # the exact setup logic already in generate_dashboard_html, moved verbatim
```

`generate_dashboard_html` becomes `ctx = build_dashboard_context(...); <compose HTML from ctx>`
(behavior-identical, verified by the existing dashboard test suite — this is a
pure extract-function refactor, not a logic change). The new `monitoring/api/`
builders take the same `ctx` and shape JSON instead. **This is the first real
implementation task of Stage 2** — everything downstream depends on it being
correct and non-regressive (run the full existing dashboard test suite after
this specific refactor, before writing a single API endpoint on top of it).

## Serving the API

`live/sse_server.py`'s `make_handler()` gains routes:

```python
def do_GET(self) -> None:
    if self.path == "/events":
        self._serve_sse()
    elif self.path.startswith("/api/"):
        self._serve_api()          # NEW
    else:
        self._serve_static()

def _serve_api(self) -> None:
    screen = self.path.removeprefix("/api/")
    builder = API_BUILDERS.get(screen)      # dict of screen name -> payload fn
    if builder is None:
        self.send_error(404); return
    conn = get_connection()                  # same real DB, read-only per request
    ctx = build_dashboard_context(conn)      # cheap: reuses cached ta/ca/sd, no beam search
    payload = builder(ctx)
    body = json.dumps(payload, default=str).encode("utf-8")
    self.send_response(200)
    self.send_header("Content-Type", "application/json")
    self.send_header("Access-Control-Allow-Origin", "*")   # same posture as /events already has
    self.send_header("Content-Length", str(len(body)))
    self.end_headers()
    self.wfile.write(body)
```

Same process, same port (`fpl live-server`, default 8877), same CORS posture
this file already documents and justifies (local-machine-only, unauthenticated,
already the case for `/events` and static files). No new dependency — still
stdlib `http.server`.

**Fallback for when the live-server isn't running** (dev, or a machine that
hasn't started the scheduled task yet): `fpl dashboard` already writes
`data/dashboard.html` on every regen; it additionally writes
`data/api/<screen>.json` for each payload at the same time, so the React app
can `fetch('/api/command.json')` against a plain static file server (like the
existing `.claude/launch.json` "dashboard" config on port 8931) with zero
backend process required for local iteration. The live-server path is additive
for real-time push, not a hard requirement to see a screen at all.

## The React app

```
frontend/
  package.json          react, react-dom, react-router (or a lighter screen switcher —
                         see note below), typescript, vite, tailwindcss, shadcn deps
  vite.config.ts         dev-server proxy: /api -> http://localhost:8877, /events -> same
  tailwind.config.ts     design tokens ported from assemble.py's :root CSS variables
                         (--accent, --accent-2, --surface, --surface-2, --border,
                         --gridline, --fg, --muted, --faint, --fpl-pink, --fpl-purple,
                         confidence/risk colors) — same palette, same names where
                         Tailwind's own token model allows it
  components.json        shadcn CLI config (created by `npx shadcn init`)
  src/
    main.tsx
    App.tsx               <Shell> wrapping the router/screen switcher
    shell/
      Sidebar.tsx          from 21st @shadcn/sidebar (§1.1 in the research doc)
    lib/
      api.ts               typed fetch() wrappers per /api/<screen> endpoint
      sse.ts                one shared EventSource('/events') hook, parsing the
                            SAME message `type` values assemble.py's current JS
                            already switches on (real, existing shapes — copy the
                            protocol, not the DOM-patching code)
      types.ts              TypeScript types mirroring each payload builder's
                            real dict shape (kept in sync by hand initially;
                            see "Nice to have" below for codegen)
    screens/
      Command/            Stat Card, Badge Delta, Status (adopted components)
      MyTeam/              Sheet, Hover Card, Radar Chart + the hand-built pitch
      Plan/                Timeline Rail, Modern Timeline
      Football/            Radar Chart, hand-built fixture/team-state views
      Scout/                Financial Markets Table, Segmented Control
      Advanced/             Records Table, Status
      Live/                 Ticker, Status, Activity Feed + hand-built match block
```

**Router note**: this is a single-user, no-auth, no-deep-linking-requirement
tool historically built as one continuously-scrolled page. A full router
(react-router) is reasonable if URLs-per-screen (`/plan`, `/scout`) are wanted
for bookmarking/refresh-to-same-screen — recommended, since it's essentially
free with Vite and matches the sidebar's own per-item `href` model from the
adopted shadcn Sidebar. Decide during Stage 2, not before.

**Charts**: the current dashboard uses ApexCharts (vendored,
`data/vendor/apexcharts.min.js`) with a real, already-audited chart-type↔
question mapping (`.claude/skills/fpl-visualization/`). ApexCharts has an
official `react-apexcharts` wrapper — **reuse it** rather than switching chart
libraries mid-migration (the existing type mapping and color-role table stay
valid; only the mounting mechanism changes from a vanilla `new ApexCharts(el,
opts)` call to the React wrapper component). The one exception is the NEW
radar-chart use case (§5.1 in the research doc) — ApexCharts also supports
`type: 'radar'` natively, so even that doesn't require a second library.
**Recommendation: zero new chart dependencies.**

## What stays exactly as-is

- Every Python module under `models/`, `optimization/`, `ingestion/`,
  `database/`, `backtesting/`.
- `monitoring/dashboard/*.py` (the HTML renderers) — kept running, producing
  `data/dashboard.html`, until each screen's React equivalent is verified
  functionally equivalent (real regression check: same authoritative
  action/path total/captain edge/etc., per this project's own established
  regression-verification habit from Phase 8.0/8.1).
- `live/sse_server.py`'s existing `/events` SSE mechanism, `DbTailer`,
  `Broadcaster` — additive routes only, no change to the existing ones.
- `live_snapshot.py`, `data_payload.py` — reused, not replaced, by the new
  payload builders.
- The Windows Task Scheduler jobs (`FPLAgentSync`, `FPLAgentLivePoll`,
  `FPLAgentLiveServer`) — unchanged; `FPLAgentLiveServer` now also serves the
  built React app's static files (point its `data_dir` at `frontend/dist/`
  once built, or add a second static root) and the new `/api/*` routes.

## Testing

- **Backend**: every new `monitoring/api/*.py` payload builder gets the same
  kind of plain dict-shape pytest coverage `data_payload.py`'s existing tests
  already use (seed a DB state, call the builder, assert the real fields) —
  no browser needed for this layer.
- **`DashboardContext` extraction**: the existing full dashboard test suite
  (`tests/test_dashboard*.py`, ~1650 tests) is the regression guard — it
  already asserts on `generate_dashboard_html`'s output for dozens of real DB
  states; if the extraction is behavior-preserving, every one of those stays
  green unchanged.
- **Frontend**: recommended but not blocking Stage 2 — Vitest + React Testing
  Library for component-level tests, Playwright (already installed and
  working for this project's own visual verification, per the Phase 8.0
  tooling note) for the cross-screen visual validation pass in Stage 10. Not
  set up speculatively before there's a real component to test.

## Nice to have (not required for Stage 1–2, flagged for later)

- **Typed API contract codegen**: hand-written TypeScript types mirroring the
  Python payload dicts are fine to start; if the payload shapes stabilize,
  generating `types.ts` from the Python dataclasses (e.g. via `dataclasses` +
  a small script, or adopting `pydantic` + `datamodel-code-generator`) would
  remove one manual-sync point. `pydantic` would be a genuinely new backend
  dependency, though a very common, lightweight one — a call for the user
  when this becomes a real pain point, not decided now.
- **OpenAPI/schema doc** for the `/api/*` routes, once there are more than a
  handful — not needed for 7 fixed, hand-known endpoints.

## Open questions for the user (before Stage 2 starts)

1. **Router**: real per-screen URLs (`/plan`, `/scout`, browser back/forward,
   refresh-stays-on-screen) via react-router, or keep the single-page feel
   with a plain in-app screen switcher (closer to today's anchor-scroll
   model, but loses shareable/bookmarkable URLs)? Recommend react-router —
   cheap, standard, and the adopted Sidebar already models per-item hrefs.
2. **npm registry access**: this environment has Node 22/npm 11 available and
   reached 21st.dev directly for research; installing `react`/`vite`/
   `tailwindcss`/shadcn deps needs standard `npm install` access to the public
   npm registry, which hasn't been exercised yet this session — worth a quick
   `npm install` smoke test at the start of Stage 2 rather than assuming it.
3. **Where does `frontend/dist/` get served from in production**: reuse
   `FPLAgentLiveServer`'s existing static-file root (point `data_dir` at the
   built assets, or serve two roots), or run the built SPA from the plain
   `data/` directory alongside `dashboard.html` during the transition? Leaning
   toward the latter for Stages 2–10 (keeps the two frontends fully
   independent while both exist), switching to the former at Stage 11.
